## 결론

Spring 5.3에서 메일 발송 비동기 처리는 **별도의 `MailAsyncService`를 두고, 메일 전용 `ThreadPoolTaskExecutor`를 지정하는 구조**가 가장 실무적입니다.

권장 위치는 다음입니다.

```text
Controller
   ↓
BusinessService
@Transactional
   ↓
업무 DB 처리
   ↓
COMMIT
   ↓
@TransactionalEventListener(AFTER_COMMIT)
   ↓
MailAsyncService
@Async("mailTaskExecutor")
   ↓
MailGateway / MailSender
   ↓
OkHttp / SMTP
```

즉, `@Async`를 Controller나 기존 업무 Service에 직접 붙이는 것보다 **비동기 경계를 별도 Service로 분리**하는 것이 좋습니다.

---

# 1. 가장 권장하는 구조

현재 메일 발송이 OkHttp를 이용한 외부 HTTP API 방식이라면 다음 구조가 좋습니다.

```text
OrderService
MemberService
SellerService
      │
      │ 업무 Transaction
      ▼
MailSendEvent
      │
      ▼ COMMIT
MailSendEventListener
      │
      ▼
MailAsyncService
@Async("mailTaskExecutor")
      │
      ▼
TemplateMailService
      │
      ▼
MailHttpGateway
      │
      ▼
공유 OkHttpClient
```

역할을 나누면:

| 계층 | 역할 |
|---|---|
| `BusinessService` | 주문/회원/기업 등 업무 DB 처리 |
| `MailSendEventListener` | COMMIT 성공 후 메일 요청 |
| `MailAsyncService` | 비동기 Thread 전환 |
| `TemplateMailService` | 템플릿, 발신자, whitelist 등 메일 업무 처리 |
| `MailHttpGateway` | OkHttp 외부 API 통신 |
| `mailTaskExecutor` | 메일 전용 Thread Pool |

이 구조에서 **비동기 전환 지점은 `MailAsyncService`**입니다.

---

# 2. 왜 `MailAsyncService`를 별도로 만드는 것이 좋은가

예를 들어 다음과 같이 구성합니다.

```java
@Service
public class MailAsyncService {

    private final TemplateMailService templateMailService;

    public MailAsyncService(
            TemplateMailService templateMailService) {

        this.templateMailService =
                templateMailService;
    }

    @Async("mailTaskExecutor")
    public CompletableFuture<MailSendResult> sendAsync(
            MailSendRequest request) {

        try {

            MailSendResult result =
                    templateMailService.send(request);

            return CompletableFuture.completedFuture(result);

        } catch (Exception e) {

            return CompletableFuture.failedFuture(e);
        }
    }
}
```

실제 외부 통신은:

```java
@Service
public class TemplateMailService {

    private final MailHttpGateway mailHttpGateway;

    public MailSendResult send(
            MailSendRequest request) {

        // 템플릿 조회
        // whitelist 확인
        // sender 결정
        // JSON 생성

        return mailHttpGateway.send(request);
    }
}
```

이렇게 분리합니다.

장점은 `@Async`가 명확하게 한 곳에 모인다는 것입니다.

# 3. 방식별 비교

## 방식 A. 기존 메일 Service에 바로 `@Async`

예:

```java
@Async("mailTaskExecutor")
public CompletableFuture<String> sendTemplateMail(
        EmailVO mailVO) {

    ...
}
```

### 장점

- 코드 변경이 가장 적음
- 구현이 단순함
- 빠르게 적용 가능

### 단점

- 템플릿 처리와 Thread 전환이 섞임
- Transaction 경계 파악이 어려워짐
- 동기 호출이 필요한 경우 재사용하기 어려움
- 테스트가 불편해짐
- 같은 클래스 내부 호출 시 `@Async`가 적용되지 않을 수 있음
- 이후 retry, callback, 상태관리 추가 시 클래스가 복잡해짐

특히 다음 구조는 문제입니다.

```java
@Service
public class MailService {

    public void process() {

        sendAsync();
    }

    @Async
    public void sendAsync() {
    }
}
```

같은 Bean 내부에서:

```java
this.sendAsync();
```

형태로 호출하면 Spring Proxy를 거치지 않으므로 **비동기로 실행되지 않습니다.**

---

# 4. 방식 B. 별도의 `MailAsyncService`

제가 현재 시스템에는 이 방식을 권장합니다.

```java
@Service
public class MailAsyncService {

    @Async("mailTaskExecutor")
    public CompletableFuture<MailSendResult> sendAsync(...) {
        ...
    }
}
```

그리고 실제 메일 처리는:

```java
@Service
public class TemplateMailService {

    public MailSendResult send(...) {
        ...
    }
}
```

로 나눕니다.

### 장점

#### 1. 비동기 경계가 명확함

코드를 보면 바로:

```text
MailAsyncService
        ↓
여기부터 다른 Thread
```

라는 것을 알 수 있습니다.

초급 개발자에게도 이해하기 쉽습니다.

#### 2. 동기/비동기 재사용 가능

같은 메일 발송 기능을:

```java
templateMailService.send(...)
```

하면 동기,

```java
mailAsyncService.sendAsync(...)
```

하면 비동기로 사용할 수 있습니다.

#### 3. Transaction 분리가 쉬움

```text
Business Transaction
        ↓
COMMIT
        ↓
MailAsyncService
```

경계를 명확히 유지할 수 있습니다.

#### 4. Executor 변경이 쉬움

현재:

```java
@Async("mailTaskExecutor")
```

나중에:

```text
RabbitMQ
Kafka
JMS
ManagedExecutorService
```

로 변경하더라도 업무 Service 영향이 작습니다.

#### 5. 테스트가 쉬움

메일 발송 자체:

```java
templateMailService.send()
```

를 동기 방식으로 Unit Test할 수 있습니다.

비동기 여부는:

```java
MailAsyncService
```

에서 별도로 테스트할 수 있습니다.

---

# 5. 방식 C. OkHttp Gateway 자체에 `@Async`

예:

```java
@Async("mailTaskExecutor")
public CompletableFuture<MailSendResult> send(...) {
    client.newCall(request).execute();
}
```

가능은 하지만 저는 권장하지 않습니다.

왜냐하면 `MailHttpGateway`의 역할은:

```text
HTTP 통신
```

이어야 하는데:

```text
HTTP 통신 + Thread 관리
```

까지 담당하게 되기 때문입니다.

계층 책임이 섞입니다.

특히 나중에:

```text
Batch
Admin
Retry Worker
재전송 프로그램
```

에서 동기 HTTP 호출이 필요할 때 재사용하기 불편합니다.

---

# 6. 방식 D. Controller에서 비동기 처리

다음은 가장 피해야 합니다.

```java
@PostMapping(...)
public ResponseEntity<?> sendMail(...) {

    mailAsyncService.sendAsync(...);

    return ResponseEntity.ok(...);
}
```

단순 테스트 용도로는 가능하지만 업무 시스템에서는 Controller가:

```text
메일 발송 시점
Transaction
재처리
업무 성공 여부
```

를 판단해서는 안 됩니다.

Controller는:

```text
HTTP 요청/응답
```

에 집중하는 것이 좋습니다.

# 7. Executor도 메일 전용으로 분리하는 것이 좋은가?

**네. 권장합니다.**

예:

```java
@Bean(name = "mailTaskExecutor")
public ThreadPoolTaskExecutor mailTaskExecutor() {

    ThreadPoolTaskExecutor executor =
            new ThreadPoolTaskExecutor();

    executor.setCorePoolSize(2);
    executor.setMaxPoolSize(4);
    executor.setQueueCapacity(100);

    executor.setThreadNamePrefix(
            "mail-async-"
    );

    executor.setRejectedExecutionHandler(
            new ThreadPoolExecutor.AbortPolicy()
    );

    executor.setWaitForTasksToCompleteOnShutdown(true);
    executor.setAwaitTerminationSeconds(30);

    return executor;
}
```

그리고:

```java
@Async("mailTaskExecutor")
```

로 명시합니다.

# 8. 공용 Executor 사용 vs 메일 전용 Executor

| 구분 | 공용 Executor | 메일 전용 Executor |
|---|---|---|
| 구현 | 단순 | 약간 증가 |
| Thread 관리 | 통합 | 독립 |
| 장애 격리 | 낮음 | **높음** |
| 메일 API 장애 영향 | 다른 Async 작업까지 영향 | **메일만 영향** |
| Queue 관리 | 혼합 | **메일 기준 튜닝 가능** |
| 모니터링 | 원인 구분 어려움 | **명확** |
| 운영 추천 | 소규모 | **현재 시스템 추천** |

예를 들어 공용 Pool이:

```text
core=10
max=20
queue=500
```

이라고 해봅니다.

메일 서버가 느려지면:

```text
메일 작업 20개 Thread 점유
       ↓
Queue 증가
       ↓
다른 Async 작업도 대기
```

할 수 있습니다.

반면:

```text
mailTaskExecutor
   ↓
SMTP/HTTP 메일 전용

otherTaskExecutor
   ↓
다른 비동기 작업
```

이면 장애가 격리됩니다.

---

# 9. 현재 시스템에서는 특히 Executor 분리가 필요한 이유

현재 메일은 내부 연산이 아니라:

```text
WAS
 ↓
TCP
 ↓
Proxy 또는 Network
 ↓
메일 API
 ↓
응답
```

형태입니다.

즉 **CPU 작업이 아니라 외부 I/O 작업**입니다.

외부 서버가 10초 느려지면:

```text
mail-async-1 → 10초 대기
mail-async-2 → 10초 대기
mail-async-3 → 10초 대기
mail-async-4 → 10초 대기
```

가 될 수 있습니다.

그래서 다른 업무용 Executor와 섞으면 안 됩니다.

현재처럼 WAS의 소켓 상태, `CLOSE_WAIT`, 504/499 문제를 분석하고 있는 환경에서는 특히 외부 네트워크 I/O Thread를 별도의 Pool로 격리하는 것이 좋습니다.

# 10. 비동기 Service의 단점도 있다

별도 Service가 무조건 장점만 있는 것은 아닙니다.

### 클래스 수 증가

기존:

```text
MailService
```

하나에서:

```text
MailAsyncService
TemplateMailService
MailHttpGateway
```

정도로 늘어납니다.

작은 시스템에서는 과해 보일 수 있습니다.

### 호출 흐름이 길어짐

```text
BusinessService
 ↓
Event
 ↓
Listener
 ↓
AsyncService
 ↓
MailService
 ↓
Gateway
```

가 되므로 처음 보는 개발자는 단순 메소드 호출보다 추적하기 어렵습니다.

그래서 클래스 이름과 책임을 명확하게 해야 합니다.

### 예외 전달 방식이 달라짐

동기 호출:

```java
try {
    mailService.send();
} catch (...) {
}
```

과 달리 비동기는 호출자에게 즉시 예외가 전달되지 않습니다.

따라서:

```text
CompletableFuture
callback
DB 상태
로그
```

등 별도 관리가 필요합니다.

## 최종 추천

두 선택지만 비교한다면:

### ① 기존 메일 Service에 `@Async`

```java
@Async
public CompletableFuture<?> sendTemplateMail(...)
```

은 **단기 수정용**으로는 괜찮습니다.

### ② 전용 Executor + 별도 `MailAsyncService`

```java
@Async("mailTaskExecutor")
public CompletableFuture<?> sendAsync(...)
```

는 **운영용 최종 구조로 더 적합합니다.**

현재 시스템에서는 **②를 권장**합니다.

가장 중요한 이유는 성능 자체보다 다음 네 가지입니다.

```text
1. 메일 외부 I/O 장애를 다른 작업과 격리
2. DB Transaction과 외부 HTTP 통신 분리
3. @Async Proxy/self-invocation 문제 방지
4. 향후 결과처리·재전송·MQ 전환이 쉬움
```

따라서 실제 구현에서는 **`mailTaskExecutor`는 Thread 자원 관리**, **`MailAsyncService`는 비동기 경계**, **`TemplateMailService`는 메일 업무 처리**, **`MailHttpGateway`는 OkHttp/socket 처리**로 나누는 것이 가장 관리하기 좋은 형태입니다.

최종본을 다시 생성했습니다. 이번 버전은 기존 생성본의 기능을 유지하면서, 사용자가 제공한 실제 메일 발송 방식인 **OkHttp 기반 템플릿 메일 API 호출 구조**로 변경했습니다.

핵심 구조는 다음과 같습니다.

```text
BusinessService
@Transactional
      │
      ├─ 업무 DB 처리
      ├─ 기존 템플릿/발신자/메일 Body 준비
      ├─ MAIL_SEND_HISTORY = PENDING
      └─ Event publish
             │
          COMMIT
```

### 이번 최종본에서 특히 변경한 부분

이전 `sendTempateMail()`의 가장 큰 문제였던:

```java
OkHttpClient client =
        new OkHttpClient()
                .newBuilder()
                .build();
```

는 완전히 제거했습니다.

이제 Spring Bean 하나를 공유합니다.

```java
@Bean(name = "mailOkHttpClient")
public OkHttpClient mailOkHttpClient() {
    return new OkHttpClient.Builder()
            .connectTimeout(...)
            .readTimeout(...)
            .writeTimeout(...)
            .connectionPool(...)
            .retryOnConnectionFailure(false)
            .build();
}
```

OkHttp는 Client를 공유하면 Connection Pool과 Thread 자원을 재사용할 수 있으므로 요청마다 Client를 만드는 방식보다 적합합니다.

또한 기존:

```java
response = client.newCall(request).execute();

String responseMessage =
        response.body().string();
```

는 다음처럼 변경했습니다.

```java
try (Response response =
             mailOkHttpClient
                     .newCall(httpRequest)
                     .execute()) {

    ...
}
```

따라서 정상 처리뿐 아니라:

```text
HTTP 오류
JSON parsing 오류
IOException
RuntimeException
```

이 발생하더라도 `Response.close()`가 보장됩니다.

이는 기존에 검토하던 `CLOSE_WAIT` 문제 관점에서도 반드시 필요한 개선입니다.

| 기능 | 결과 |
|---|---|
| `mailTaskExecutor` | 유지 |
| `mailResultTaskExecutor` | 유지 |
| bounded Queue | 유지 |
| `AbortPolicy` | 유지 |
| MDC 전달/정리 | 유지 |
| graceful shutdown | 유지 |
| `CompletableFuture` | 유지 |
| `Future.get()/join()` 금지 | 유지 |
| `AFTER_COMMIT` | 유지 |
| 결과 DB `REQUIRES_NEW` | 유지 |
| `PENDING → SENDING` 원자적 선점 | 유지 |


가 추가되었습니다.

### 특히 현재 시스템 때문에 추가한 개선

현재 시스템은 Service 계층에 광범위한 `REQUIRED` Transaction advice가 적용될 가능성이 있으므로, 외부 HTTP 호출 클래스가 실수로 전역 Transaction 대상이 되는 것을 막기 위해 구현 패키지를 분리했습니다. 

```text
mail.async
    MailAsyncService

mail.gateway
    TemplateMailHttpGateway

mail.orchestration
    MailSendCoordinator

mail.state
    MailSendStateManager

mail.dispatch
    MailDispatchManager
```

즉 일반적인:

```text
..service..*
```

형태의 기존 Transaction pointcut에 외부 HTTP 호출 경로가 우연히 포함될 가능성을 줄였습니다.

다만 실제 XML pointcut이 더 넓다면 반드시 확인해야 합니다.

예를 들어 이런 식이라면:

```xml
<aop:pointcut
    expression="execution(* ..service..*(..))"/>
```

이번 패키지 분리가 효과적입니다.

반대로:

```xml
execution(* com.xxx..*(..))
```

처럼 전체 Bean을 대상으로 한다면 별도 제외가 필요합니다.

### 기존 `sendTempateMail()`은 이렇게 분할하는 것이 좋습니다

기존 메소드:

```text
whiteList 검사
template DB 조회
sender 복호화
mailVO 변경
메일 Body 생성
OkHttpClient 생성

```

를 그대로 `@Async`로 만들지 않았습니다.

다음처럼 분리했습니다.

```text
[동기 영역]

whiteList 검사
template 조회
sender 복호화
메일 Body JSON 완성
        ↓
PreparedTemplateMailRequest 생성
        ↓
PENDING 등록
        ↓
Event

---------------- Transaction COMMIT ----------------

[비동기 영역]

MailAsyncService
        ↓
PENDING → SENDING
        ↓
OkHttp HTTP POST
        ↓
SUCCESS / FAIL
        ↓
callback
        ↓
결과 DB
```

가장 중요한 이유는 기존 `EmailVO`가 mutable 객체이기 때문입니다.

다음처럼 하지 않습니다.

```java
@Async
public void send(
        EmailVO mailVO) {
```

대신 비동기 실행 전 이미 완성된 JSON을:

```java
PreparedTemplateMailRequest
```

에 넣어 전달합니다.

```java
public final class PreparedTemplateMailRequest {

    private final String requestId;
    private final String businessKey;
    private final String templateCode;
    private final String mailBody;
    private final int recipientCount;
}
```

따라서 비동기 Thread와 원 요청 Thread가 같은 `EmailVO`를 수정하는 경쟁조건을 제거했습니다.

### 최종 검증

생성 후 다음 항목을 다시 검사했습니다.

```text
Java 파일 brace 구조
MyBatis XML parsing
삭제/변경된 클래스명 잔존 여부
Future.get()
Future.join()
기존 클래스명 reference
```

최종 결과:

```text
Validation: OK
```

입니다.

다만 프로젝트의 실제:

```text
OkHttp 버전
EmailVO package
CodeService package
CryptoUtil
json-simple
eGov Mapper 설정
XML Transaction pointcut
```

까지 연결한 전체 Maven compile은 현재 프로젝트 classpath가 없기 때문에 수행하지 않았습니다.

Spring 5.3에서 `@Async`는 특정 Executor 지정과 `CompletableFuture` 반환을 지원하며, `ThreadPoolTaskExecutor`의 bounded queue와 rejection 관리도 지원합니다.  `AFTER_COMMIT` Listener는 원 Transaction이 이미 완료된 뒤 실행되므로 이후 메일 결과 처리는 별도 Transaction으로 분리해야 한다는 점도 이번 구조에 그대로 반영했습니다. 

이번 버전을 기준으로 적용하면 됩니다.
